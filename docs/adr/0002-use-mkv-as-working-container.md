# ADR 0002: 錄影進行中強制以 MKV 作為安全工作容器

## 狀態 (Status)
已採納 (Accepted)

## 背景與問題脈絡 (Context)
一般螢幕錄影工具常見的問題是：直接將畫面與聲音即時編碼寫入 MP4 檔案。
傳統 MP4 容器依賴位於檔案結尾（或開頭）的關鍵元資料區塊 `moov atom`。如果錄影過程中發生：
- 系統突然當機或斷電
- 使用者從工作管理員強制結束程式 (End Task)
- 顯示卡驅動崩潰、記憶體耗盡
- 磁碟空間意外填滿

則 MP4 檔案將因缺少完整的 `moov atom` 而導致整個錄影檔案毀損，已錄製數十分鐘甚至數小時的資料全部遺失（符合 AGENTS.md 嚴格禁止的 S0 級重大故障）。

## 決策 (Decision)
1. **錄影進行中嚴格使用 Matroska (MKV) 作為主要安全工作檔案** (`recording.mkv`)。
2. MKV 容器基於 EBML (Extensible Binary Meta Language)，其音訊與視訊資料是以獨立的「Cluster」單位連續寫入磁碟。
3. 即使錄影過程中程式遭到 `kill -9` 或電力突然中斷，所有截至中斷當下已寫入磁碟的 Cluster 均具備完整的時間戳記與可讀性，無需等待錄影停止寫入尾端 Header 即可由任何標準播放器直接播放。
4. 錄影正常停止後，才啟動無損轉換作業：
   ```text
   MKV (安全工作檔) ──[ Stream Copy: -c copy ]──> MP4 (最終輸出檔)
   ```
5. 轉換完成後，先透過 `ffprobe` 檢驗 MP4 的有效性與音畫長度；唯有在 MP4 驗證成功後，才依使用者設定決定保留或刪除工作 MKV。

## 替代方案評估 (Alternatives)
- **直接寫入 FastStart MP4 (fMP4 / Fragmented MP4)**：
  - 優點：副檔名為 `.mp4`，片段損毀不會影響整段。
  - 缺點：若片段切換時中斷，部分傳統播放軟體相容性較差，且某些舊版播放器對非標準終止的 fMP4 容易產生 seek 錯誤；相比之下，MKV 是各大開源與專業影音軟體（OBS 等）公認最強韌之即時錄影防崩潰容器。

## 後續影響與風險 (Consequences & Risks)
- **優點**:
  - 完全杜絕錄影中斷導致整段影片全毀的 S0 災難。
  - 完美支援 Crash Recovery，即便斷電重開也能百分之百救回中斷前的錄影內容。
- **後續處理**:
  - 需要在錄影結束時排程執行極速 Remux（因為是 `-c copy` 無損流複製，耗時極短，例如數 GB 檔案僅需幾秒至十餘秒），使用者體驗良好。
