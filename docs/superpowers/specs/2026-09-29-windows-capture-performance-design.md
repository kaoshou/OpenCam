# Windows 錄影效能與游標穩定性設計

日期：2026-09-29

參考基準：`fd1f1f891602d80138adecb482483b634299d1e4`（v0.2.3）

狀態：方向已獲同意；本書面設計待審閱，尚未進入實作。

## 1. 目的與證據界線

改善部分 Windows 電腦錄影時的游標閃爍及不必要 CPU 負載，同時保留錄影、錄音、暫停續錄、多螢幕、自訂選區及救援能力。macOS 擷取與音訊傳輸不改寫；共用元件的調整必須通過 macOS 回歸。

使用者提供的情境：Windows、1920×1080、30 FPS、編碼器「自動選擇」、預設游標、內顯，錄影當下實際螢幕上的游標閃爍，CPU 使用率約 8%。CPU 型號、GPU 型號與 8% 的程序統計範圍未取得；使用者目前無法做額外測試。

既有日誌 `app-20260929.log` 可確認：

- 7 次錄影／分段啟動均為 `gdigrab -draw_mouse 1` 搭配 `libx264 -preset veryfast -crf 23`，不是硬體編碼。
- 有 9 次 IPC 寫回時的 `Pipe is broken`，主要出現在暫停／繼續附近；隨後仍有狀態查詢。
- 沒有各硬體編碼探測的失敗原因，也沒有 CPU/GPU 效能量測，不能宣稱已證實硬體被誤判或全部 8% 來自編碼。
- 沒有隱藏游標的對照測試。FFmpeg 上游曾討論 `gdigrab` 的 `CAPTUREBLT` 路徑造成實際游標閃爍，與症狀相符，但不是此電腦的實測證明。

不得把「內顯」等同於「沒有硬體編碼」，也不得把 1080p／30 FPS 當作應由使用者降低的錯誤設定。原始日誌不提交至 Git，以免公開使用者本機資訊。

## 2. 決策與交付切分

採用三個可分開審查、測試及回退的子專案，依序交付：

1. **編碼偵測與診斷**：統一偵測實作、可靠地管理探測程序、顯示實際結果。
2. **控制與狀態查詢分離**：避免耗時控制操作阻塞短時限查詢，保留所有 IPC 安全防護。
3. **Windows 新擷取路徑**：以 FFmpeg `ddagrab` 導入 Desktop Duplication，GDI 保留為預設／備援，完成驗收後才另行決定是否改預設。

後續各子專案分別撰寫實作計畫；本文件不是一次授權修改全部元件或發布版本。第一、二階段可獨立交付，不宣稱因此已修復 GDI 游標閃爍。

不採用直接移除 `CAPTUREBLT`：它影響分層視窗的擷取，且所用 FFmpeg 版本沒有可直接依賴的 `use_captureblt` 選項。不在本次全面改寫原生 Windows 擷取引擎或自建修改版 FFmpeg。

## 3. 不變條件

- 保留 MKV 工作檔、驗證後 MP4 無損封裝、既有救援與防覆寫保護。
- 保留四種音訊模式、系統聲音與麥克風的獨立控制及波形顯示。
- 不移除 HMAC、程序身分檢查、重播防護、認證期限、連線與訊息大小限制。
- 不偷偷降低解析度、FPS、畫質，亦不永久隱藏游標作為閃爍修正。
- 本次設計不變更版本號、依賴版本、FFmpeg 來源或授權；發布另依使用者指示及驗收結果處理。
- 已存在的兩份未追蹤計畫文件不改動、不納入本次文件提交。

## 4. 子專案一：統一編碼器偵測

### 現況與元件責任

`FFmpegEncoderDetector` 用於介面，`FFmpegScreenRecorderEngine.QuickProbeEncoder` 用於錄影啟動。兩者的逾時分別為 2.5 秒與 1.5 秒，均有重新導向但未排空的輸出，且未完整處理逾時後的程序生命週期。

新增共用的探測執行元件，負責啟動、非同步排空輸出、計時、取消、退出碼與結果分類；偵測器負責候選選擇及快取，錄影引擎不再保有另一份探測實作。

UI 與 Recorder 是不同程序，不把程序內快取誤當成跨程序共享。兩者使用相同政策；Recorder 的實際啟動結果是權威，UI 的預先偵測只是可用性提示。

### 行為要求

- 結果至少區分可用、探測失敗、逾時、使用者取消與程序啟動失敗。沒有明確證據時不得把一般失敗標成「硬體不支援」。
- 使用有上限的非同步等待；逾時與取消都要終止自己啟動的探測程序並等待清理，不按名稱終止其他 FFmpeg。
- 輸出必須持續排空；只保留有界診斷尾端，不能為排錯無限制占用記憶體。
- 探測預算、清理期限與快取失效規則在第一階段實作計畫中定義為可測試的固定政策，不只是任意加長目前等待時間。
- 在 Recorder 生命週期內重用有效結果；不得每次續錄重新跑整套探測。FFmpeg 路徑／版本改變或正式硬體啟動失敗時，結果失效。
- 手動選擇 CPU 必須維持 CPU；「自動」優先採用已驗證可用的硬體候選。正式啟動仍可能失敗，保留既有安全回退。
- 不在已產生有效片段後任意切換編碼器而破壞後續 stream-copy 合併。續錄無法維持相容輸出時，留在可恢復的暫停狀態並提示，不覆寫既有片段。
- 日誌記錄候選、退出碼、耗時、失敗分類、經限制的錯誤內容，以及最終選擇／回退原因。不得記錄 IPC 金鑰。
- 在中英文狀態區顯示實際編碼器；尚未啟動時標示尚未決定，不能將使用者選的「自動」冒充實際結果。

### 驗收

以可控測試子程序覆蓋：正常成功、非零退出、大量 stdout/stderr、延遲初始化、逾時、取消、啟動失敗與重複探測。驗證沒有管線阻塞、殘留程序及無限快取錯誤；另以實際 FFmpeg 驗證可用編碼器，不把模擬成功當作硬體驗收。

## 5. 子專案二：控制指令與狀態查詢分離

### 設計

目前控制、遙測與音量查詢共用 `_messageGate`。耗時控制操作可使 500 毫秒的波形查詢及 1.5 秒的遙測查詢先斷線，服務端後續寫回便遇到破管。這是與日誌吻合的機制，實作前須以阻塞控制處理器重現。

- Start／Stop／Pause／Resume／UpdatePausedConfiguration 等有副作用操作仍序列執行，保留狀態機約束。
- GetTelemetry／GetAudioLevels 完成同樣的認證後，讀取不可變、執行緒安全的快照，不進入耗時控制鎖。
- 快照由狀態／音量更新來源發布，包含工作階段身分與更新時間；查詢不得當場進行媒體探測、磁碟掃描或等待啟動完成。
- 以快照的新鮮度處理延遲：介面保留最後值並明確表示暫時未更新，不把舊波形顯示為持續正常收音；不得把上一工作階段資料套用到下一場錄影。
- 每類 UI 查詢最多一個進行中請求；過期查詢不重試堆積。單次查詢失敗不得觸發停止或重複錄影控制。
- 已認證客戶端逾時／取消與真正程序退出、傳輸損壞及認證失敗分別診斷。不能只把所有錯誤降級或吞掉。
- 不將有副作用命令當成只讀查詢，不取消伺服器資源限制；認證失敗不得取得狀態或占有控制鎖。

### 驗收

控制處理器故意延遲超過查詢期限時，已認證查詢仍能讀取一致快照；未授權查詢仍被拒絕。覆蓋多客戶端、取消、離線、停止與續錄交錯、新舊 Session 切換、退出清理，並重跑現有 IPC 安全測試。

## 6. 子專案三：Windows Desktop Duplication

### 啟用與相容性

新增只在 Windows 顯示的進階設定：

- **相容擷取（GDI）／Compatible capture (GDI)**：既有預設；舊設定沒有此欄位時亦採用 GDI。
- **新版擷取（測試）／Modern capture (experimental)**：優先嘗試 `ddagrab`，不支援時依下述規則備援。

通過 Windows 實機矩陣前不改成全體使用者的自動預設；設定只在待機可變更，開始及暫停時都鎖定。macOS 不顯示或套用此設定。

### Windows 元件邊界

由 Windows 專屬的能力檢查、螢幕對應與擷取計畫產生元件處理 D3D11／DXGI；Core 只承載平台無關設定與實際模式資訊，不引用 Windows API。

建立一份明確的啟動計畫，將擷取方式、GPU／輸出識別、座標、像素格式轉換、編碼器及音訊輸入映射一起驗證；不只在原本輸入字串替換 `gdigrab`，卻讓輸出仍假設普通記憶體畫格。

- 核對所用 FFmpeg 的 `ddagrab` 能力與實際啟動結果，不以套件名稱判定可用。
- 將既有 Windows 顯示器裝置名稱與實體矩形對應 DXGI adapter/output。不得直接將 `MonitorIndex` 當成 `output_idx`，亦不得無法對應時默認主螢幕。
- 初期支援任一可正確對應的單一螢幕，以及完全落在該螢幕內的選區；全螢幕模式若橫跨多個輸出，與跨螢幕選區一樣使用 GDI。
- 桌面絕對實體座標轉為輸出相對座標，處理負座標、DPI、旋轉及裁切邊界。無法證明對應正確的組合採用 GDI，不能輸出錯誤區域。
- `ddagrab` 產生 D3D11 畫格。依編碼器能力明確決定硬體互通或 `hwdownload`／色彩格式轉換；第一版不承諾零拷貝或所有 GPU 互通。不得將 NVIDIA 成功推定為 Intel／AMD 成功。
- 系統音訊、麥克風與游標設定沿用現有語意，維持音訊輸入索引、混音、時間戳與分段規則。驗證隱藏、預設、光圈及點擊波紋，不漏錄分層視窗。

### 回退與故障處理

- 開始前確定不支援、跨輸出、對應不明或 GPU 不相容：選 GDI，顯示原因。
- 首次啟動在第一個有效片段前失敗：停止並回收失敗程序，使用獨立試啟動檔名，確認未覆寫既有資料，再有限次嘗試 GDI。
- 已產生有效片段後，或續錄時原後端失效：不無聲切換後端／編碼器。保留已有 MKV，安全停止或回到可恢復的暫停狀態並提示。
- 螢幕拔除、模式變更、鎖定或 DXGI 存取失效必須觸發有界故障處理，不能無限送出舊畫格仍顯示正常錄影。
- 狀態區與日誌顯示實際擷取方式、編碼器與回退原因；不能宣稱採用了新版而實際使用 GDI。

## 7. 驗收方法與發布門檻

### 自動化

執行各子專案的失敗重現與回歸測試、完整 .NET 測試、網站／版本／封裝測試、Windows／macOS／Linux CI。Windows 的螢幕座標、adapter/output 對應、範圍檢查、參數及備援決策可自動測試；合成畫面只能驗證管線，不能證明真實游標閃爍已消失。

### Windows 硬體矩陣

至少涵蓋可用的 Intel／AMD 內顯、NVIDIA、無硬體編碼、單／多螢幕、不同 DPI、負座標、旋轉、跨螢幕選區及多 GPU 對應。無相應硬體的列明確標示 `BLOCKED`，不要求目前無法測試的使用者立即補測，也不將缺測列改成通過。

對可取得的環境比較 GDI 與新版擷取：相同 1080p／30 FPS、畫質、音源與測試內容，先暖機再量測穩態區段，各組至少 3 次。記錄 CPU 型號、邏輯處理器數、GPU／驅動、電源模式、OpenCam UI／Recorder／FFmpeg 各自及合計 CPU、GPU 編碼使用率、FPS、掉幀、啟動／停止耗時與音畫同步；不混用不同 CPU 百分比計算口徑。

每種音訊模式至少 5 分鐘，另測暫停切換音源與游標、重複開始停止、至少 30 分鐘基本長錄、Recorder 強制中斷後救援、FFmpeg 失效、拔除螢幕及 remux 失敗。保存影片、日誌、ffprobe 結果、比較數據；不得破壞使用者既有錄影。

通過條件：

- 範圍、游標、四種音訊模式及分段合併正確；不增加資料遺失、漏音、卡死或殘留程序。
- IPC 改動不得造成安全測試退步。
- 有問題的硬體上若尚未驗證游標，發布說明不能宣稱已普遍解決閃爍。
- CPU 改善以同機多次比較數據說明，不承諾從 8% 降至指定值。任何穩定可重現的掉幀／同步／資源退步都阻止新版擷取升為預設。
- 三階段可分開合併／發布；Windows 新後端可以維持測試選項。無 Windows 硬體證據時不以 CI 綠燈取代實機驗收。
